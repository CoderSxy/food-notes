# PC 与移动 Web 改版详细方案

日期：2026-10-31。状态：用户已确认并授权实施；实现及验证状态见对应 progress 文档。

## 1. 目标与决策来源

- 用户已确定：PC、移动 Web 都参考 workbuddy-manager 的页面结构；首页两张卡片展示餐饮、物品数量；同一张地图展示餐饮及有位置的物品；菜单包含记录、增加、AI 推荐及账号；无 token、过期或无效 token 跳转登录。
- 用户已确定：首页默认「我的」，同时保留「全部」切换。
- 按用户原始要求设计：token 存入 localStorage，服务端验证后进入系统。此前提出的 HttpOnly Cookie 保留方案未获确认，不作为本方案主路径。
- 以下导航细节、断点、分页大小、接口路径为设计建议，随本方案一起审阅。
- 保留 Next.js 15、React 19、Supabase、jose、Leaflet/react-leaflet；不重建业务数据库，不更换地图供应商。

## 2. 现状及改造原因

当前 app/layout.tsx 全局提供顶部导航，登录页也共享；首页同时承担介绍、附近查询、地图和列表。首页未登录时显示引导，不直接跳登录。登录页已登录时显示账号面板，不自动进入系统。

entries 已统一餐饮 place、物品 item；餐饮必须有坐标，物品可无坐标。首页地图已存在，但使用最新最多 100 条列表数据，且「我的」在浏览器内过滤，可能漏掉较早的个人记录。统计不能基于这 100 条计算。

当前登录以 food_session HttpOnly Cookie 保存 30 天 JWT，接口通过 requireUser() 读取 Cookie。迁移 localStorage 需要同时修改两种登录方式、请求工具、接口鉴权和新增页的服务端 Cookie 检查；不能只改首页。

参考来源：
- https://github.com/ithtelab/workbuddy-manager/blob/main/web/app/(main)/layout.tsx
- https://github.com/ithtelab/workbuddy-manager/blob/main/web/components/common/layout/ManagementBar.tsx
- https://github.com/ithtelab/workbuddy-manager/blob/main/web/components/ui/floating-dock.tsx

参考仓库采用居中内容区、PC 底部 Dock、手机右下展开导航；本方案借用结构并按记录与地图场景调整，不引入其账号池等业务。

## 3. 方案比较

| 方向 | 布局与取舍 |
| --- | --- |
| A，推荐 | PC 底部 Dock；手机右下菜单向上展开。接近参考结构，地图展示空间充足；手机切页需要先展开 |
| B | PC Dock；手机常驻底部五项导航。手机入口更直观，但地图可用高度减少，与参考结构不同 |

## 4. 页面与路由

| 路由 | 页面 | 核心内容 |
| --- | --- | --- |
| / | 首页总览 | 范围切换、两张统计卡片、一张记录地图 |
| /entries | 记录 | 分类、范围、关键词、分页列表 |
| /entries/new | 增加记录 | 餐饮/物品表单及选点地图 |
| /entries/[id] | 记录详情 | 分类、评分、标签、备注、位置、本人删除 |
| /recommend | AI 推荐 | 位置、半径、附近餐饮推荐结果 |
| /account | 账号 | 用户信息、退出登录 |
| /login | 登录 | 账号密码为主、现有测试验证码为次要方式 |

系统页面共享 AppShell；登录页独立。用 App Router 路由组组织，不改变以上地址。保留 /foods/new、/foods/[id] 的旧地址跳转与旧 API 餐饮兼容行为。

主菜单顺序固定：首页、记录、增加、AI 推荐、账号。增加页和详情页高亮各自所属入口；详情归属「记录」。手机菜单每项显示图标与文字，点击、点击外部、Escape 或路由变化后关闭，并保持正确的焦点管理。

## 5. 首页结构与响应式规则

内容顺序：简洁页头「总览」与用户信息 → 我的/全部切换 → 两张统计卡片 → 地图标题与类型筛选 → 地图 → 地图覆盖说明。首页不放完整记录列表、经纬度输入表单或大幅介绍区。

PC：内容区居中，建议最大宽度 1280px；两卡片等宽；地图为主视觉；Dock 固定底部居中。

手机：页面水平留白 16px；两卡片仍并排，名称、数量、单位不横向溢出；地图建议高度 clamp(320px, 56dvh, 560px)；右下菜单避开地图控件。常规桌面地图建议高度 clamp(420px, 60dvh, 760px)。小屏或横屏允许页面纵向滚动，不强制一屏塞完。

建议以 768px 区分手机与 PC 导航，列表在 768px、1024px 逐级从一列变为两列、三列。表单最大宽度约 720px；账号与登录约 440px。所有页面为导航、手机安全区及软键盘预留空间。

视觉采用参考项目的简洁应用结构、清楚的文字层级、克制圆角及浅色分区。按用户后续要求使用微软雅黑优先、苹方/Segoe UI/Arial/系统无衬线回退，移除 Google Fonts 加载及字体包。继续保留产品「美食地图」名称；餐饮、物品以图标和点缀色区分，不只依赖颜色。深色主题切换不列为本轮必做。

## 6. 范围、数量与筛选口径

- 新访问首页默认 scope=mine；显式 scope=all 才展示全部。选择写入 URL，不自动从 localStorage 恢复为「全部」。刷新显式 URL、前进后退保留 URL 状态。
- 「我的」：服务端以已验证 token 的用户 ID 过滤 user_id；不接受客户端传入任意 userId 代替鉴权用户。
- 「全部」：所有登录用户可见的共享记录，沿用当前权限；切换范围不增加编辑或删除权限。
- 范围同时影响两张统计卡片、地图和从首页进入的记录列表。
- 餐饮卡片显示餐饮记录条数，物品卡片显示物品记录条数；单位统一「条」，不把一次记录误称为一家独立店铺。
- 物品总数包含无位置物品。地图只含有效成对坐标的记录，0 纬度/经度仍合法。
- 地图类型筛选 all/place/item 只影响地图点位，不改两张总量卡片；卡片始终展示当前范围的两类总数。
- 点击餐饮卡片进入 /entries?scope=mine&kind=place，物品同理；scope 随当前选择变化。
- 默认首页地址 / 等价于 /?scope=mine&kind=all。列表使用独立 URL 保存自己的筛选，不让列表关键词影响首页总数。

地图说明示例：「当前范围共 204 条记录，其中 150 条有位置，54 条未记录位置」。数字必须来自服务端统计；选中类型后说明限定该类型。加载失败显示「—」与重试，不能显示为 0。

## 7. 地图交互与数据完整性

复用现有地图与选点能力。餐饮用餐饮图标，物品用物品图标；图例同时提供类型文字。同位置记录聚合，点击聚合簇缩放或展开重合点。现有依赖没有聚合插件，实施时选择兼容当前 React/Leaflet 的最小方案，确定依赖后纳入检查。

首次加载/切换范围或类型后适配有效点边界；单点设置合理最大缩放。用户拖动、缩放或定位后，普通数据刷新不反复重置视角。新增记录后回首页可通过显式「查看全部点位」重新适配。

点位弹窗展示名称、餐饮/物品类型、评分、地址摘要和详情入口。手机点位预览使用地图下方的可关闭摘要卡片，避免小弹窗难以触达；只有点击详情入口才导航。

主动点击「定位到我」才申请定位，不把当前位置作为默认数据过滤条件。定位拒绝、超时或不支持时提示原因，保留记录地图。查看附近餐饮的入口放在记录页和 AI 推荐页。

首页地图用独立轻量数据接口，不受列表 100 条限制。第一版按稳定游标每批 500 个点位递进加载，游标按 created_at 与 id 形成唯一顺序；服务端范围、类型过滤先于分页。返回 hasMore/nextCursor，直到加载完成才宣称完整展示。

加载后续批次时保留现有点位，提示「已加载 X / Y 个点位」；失败提供继续加载，不把部分结果当全部。范围或类型变化取消旧请求，并防止旧响应覆盖新范围。首批加载后地图可交互，完整加载或用户主动操作时再统一适配视角，避免每批跳动。

本轮不做按视口加载、热力图、路线、离线地图。记录量超出全量点位适用规模时，后续升级视口查询与服务端聚合；不得静默截断。地图数据与统计分别查询，不承诺并发新增/删除时的数据库快照一致性；完成加载后复核统计并提示刷新。

保留 OpenStreetMap 署名、现有底图配置及地图错误回退。地图瓦片失败时保留统计、菜单与「查看记录」入口。

## 8. 记录、增加、详情与 AI 推荐

记录页：默认我的，支持全部；类型全部/餐饮/物品；按名称关键词搜索；最新优先、created_at 与 id 稳定排序；每页 20 条、提供上一页/下一页；改变筛选回第一页。PC 多列卡片，手机单列。附近查询明确「仅餐饮」，要求定位或选点；列表分页与附近结果模式分开标识，附近模式沿用现有 5 公里及最新 500 条候选限制，并展示覆盖说明，不宣称全量附近搜索。

增加页：沿用餐饮/物品切换；餐饮保留菜系与必填坐标，物品保留两级分类与可选位置；共用名称、半星评分、标签、地址和备注。手机单列，PC 表单与选点可分区；不改变数据校验约束。提交中防重复，失败保留填写内容，成功进入详情并使首页/列表缓存失效。详情提供「继续记录」和返回记录列表入口。

详情页：保留现有全部字段、有坐标小地图、本人删除。返回列表时携带来源范围和筛选；直接访问没有来源时返回默认「我的」列表。删除后返回原列表并更新总数和地图；他人记录不显示删除按钮，服务端仍校验所有者。编辑记录不在本轮范围。

AI 推荐：独立菜单入口；保留现有 1/5/10/20 公里、只推荐有位置餐饮、最多 30 个 AI 候选及最多 5 项结果的规则。推荐仍使用大家共享的餐饮记录，与首页范围独立，页面明确写「从全部共享餐饮记录中推荐」。不增加物品 AI 推荐或新的偏好问卷。保留无样本不调用 AI、上游失败可重试；现有附近查询最新 500 条限制作为已知边界展示。

账号页：显示昵称、用户名及现有可用联系方式，缺失字段不编造；提供退出。退出请求完成后清理本地 token、用户与业务缓存，回登录页。修改密码、注册与头像上传不在本轮范围。

## 9. localStorage token 与登录流程

存储键建议 food-notes:access-token。两个登录方式均返回 accessToken、expiresAt、user，统一写入。JWT 延续当前 HS256、issuer/audience food-notes、30 天过期规则；签名密钥只在服务端。用户信息缓存不等价于有效登录。

进入系统：读取 token → 不存在则 replace 到 /login?next=站内目标地址 → 存在则调用 /api/auth/me，由服务端验证签名、过期时间、issuer、audience 及用户是否存在 → 验证成功挂载系统内容。客户端可提前识别明显过期/损坏，但不能凭解码结果放行。

登录页有 token 时也先验证；有效则 replace 到合法 next 或首页，无效则清理后显示表单。登录成功返回原目标；next 只接受本站根路径，拒绝 //、外站 URL、登录页回环和可导致外站跳转的编码形式。校验阶段统一加载态，网络/5xx 保留 token，显示重试，不误判退出。

请求统一携带 Authorization: Bearer <token>，只向本站业务 API 附加；不向地图瓦片或外部 AI 服务发送。所有业务 API 改为基于请求头鉴权，登录/发码/验码保持必要公开入口。匿名 API 仍返回 401 JSON，不由 API 返回登录页 HTML。旧 foods API 同样迁移；响应字段及餐饮限制保留，旧 Cookie-only 调用不再支持。

401：统一清理缓存并去登录，同一批并发失败只触发一次跳转；登录接口用户名密码错误显示表单错误。403：显示权限不足；404：记录不存在；5xx/断网：重试，不清 token。首次验证后，使用到期定时检查、页面重新可见时复核及业务 401 处理失效，不需要每次切页都重新验证。

跨标签页监听 storage 事件；退出后其他标签页清理状态，新 token 写入后重新验证，不接受旧账号数据残留。切换账号及退出时取消旧请求、清除范围内缓存。token 禁止写入 URL、日志或用户界面。

迁移时移除依赖服务端 Cookie 的页面守卫，以共享客户端 AuthProvider/AuthGate 保证界面跳转，API 服务端鉴权保证数据权限。服务端渲染不读取 localStorage，不输出受保护业务数据；只输出稳定加载壳，避免 hydration 分歧。两种登录响应和业务 API 需同步发布，避免半迁移。登录、退出时清除遗留 food_session Cookie，旧会话用户重新登录一次；不把 Cookie 与 localStorage 当成两套可独立放行的会话。

localStorage 可被同源 JavaScript 读取，这是相对当前 HttpOnly Cookie 的安全取舍；实施需避免不可信 HTML 注入。退出按当前能力是移除浏览器凭证，不保证已复制 JWT 立刻失效；本轮不新增服务端会话撤销表或 refresh token 机制。

## 10. API 设计建议

| 接口 | 建议契约 |
| --- | --- |
| GET /api/dashboard/summary?scope=mine | 返回 scope、placeCount、itemCount、mappedPlaceCount、mappedItemCount；都为当前范围的数据库精确计数，不受分页影响 |
| GET /api/entries/map?scope=mine&kind=all&cursor=... | 返回轻量 points、nextCursor、hasMore；每批最多 500；点含 id、kind、name、rating、lat、lng、address_text、created_at |
| GET /api/entries?scope=mine&kind=place&q=...&page=1&pageSize=20 | 返回 entries、total、page、pageSize；pageSize 上限 100，q 最长 100 字；kind 省略代表全部，非法参数返回 400 |
| POST /api/auth/login、/api/auth/verify-otp | 返回 ok、accessToken、expiresAt、user，不再创建新登录 Cookie |
| GET /api/auth/me | 验证 Bearer token 与用户存在性，返回安全用户字段 |
| POST /api/auth/logout | 前端完成本地清理；服务端清理遗留 Cookie，不宣称能撤销签发过的所有 JWT |

统一 scope 缺省 mine；显式 all 才共享浏览。原 GET /api/entries 省略 scope 时原为全部，属于有意改变，需同步更新内部调用、测试和 README。旧 /api/foods 数据范围语义保持原样；附近及推荐接口按第 8 节保留，不隐式继承首页 scope。统计、分页、关键词与点位由服务端执行；前端不依赖下载全部用户完整记录后再筛「我的」。

索引按现有数据库结构检查后补充，候选为 (user_id, created_at, id)、(created_at, id) 及有坐标的部分索引；可增加索引迁移，不新建业务表。计数为 0 与查询失败要区分。所有用户数据响应明确 no-store，或采用按当前用户隔离的缓存并在登录切换时清除。

## 11. 代码职责与实施顺序

1. 登录与布局：调整 lib/auth/requestUser.ts、lib/browser.ts、两种登录 API、me/logout 及全部受保护 API；新增 token 存储与 AuthProvider/AuthGate；拆分登录/系统布局；移除新增页 Cookie-only 守卫。先确保无 token/无效 token/有效 token 流程一致。
2. 统计与查询：扩展 lib/entries.ts、查询参数校验、统计/地图 API；实现服务端 scope、精确计数、稳定分页和轻量点位，按需补索引。
3. 系统导航：首页/记录/增加/AI 推荐/账号，PC Dock 与移动展开菜单；统一页头与内容容器。
4. 首页：重组 app/page.tsx 与地图组件，接入两张卡片、范围联动、类型筛选、聚合和完整加载提示。
5. 页面迁移：新增 /entries、/account，适配新增、详情、推荐、登录；处理来源返回、保存/删除后刷新及旧地址兼容。
6. 验证与交付：自动检查、真实浏览器多尺寸验证，更新 README；产品功能实现与本设计文档交付分开，不在方案阶段改业务代码。

组件建议按职责拆分 AppShell、AppDock、PageHeader、OwnerScopeSwitch、SummaryCards、DashboardMap、EntriesList；复用现有 EntryForm、EntryCard、评分和选点组件。路由移动引起的测试引用需同步更新，不同时做无关重构。

## 12. 验收标准

- 首页初次默认我的，可切全部；统计、地图和进入列表的 scope 一致；显式 URL 刷新/前进后退正确。
- 两张卡片来自真实总数；创建超过 100 条数据后，个人较早记录仍可被查询和上图；无位置物品计入数量而不上图。
- 地图全部/餐饮/物品筛选正确；零坐标合法；同位置点可展开；定位拒绝、瓦片失败不影响列表入口。
- 点位多批加载完整且有进度；中途失败可以继续；快速切换范围无旧响应覆盖；边拖地图边刷新不会突然跳回。
- 记录列表按服务端范围、类型、关键词分页；无关键词结果与无记录显示不同提示；列表空态提供增加入口。
- 无 token、过期、篡改、用户已删除均无法访问业务数据；有效 token 进入系统；已登录访问登录页自动返回；网络/5xx 不清 token。
- Authorization 不发送至外站；next 外站与编码绕过被拒绝；退出、切换账号和跨标签页同步不残留前一账号数据。

- PC 与手机均可完成登录、浏览、选点、新增、详情、删除及 AI 推荐；手机菜单不遮住关键地图控件和提交按钮。
